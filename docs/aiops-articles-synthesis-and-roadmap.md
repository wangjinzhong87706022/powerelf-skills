## 一、文章总结

### 1.1 文章一：数据治理 AI 智能体落地手册（概念框架）

**核心主张**：数据治理不是「一堆工具」，而是一个「被 Agent 驱动的闭环治理平台」。
文章把企业数据治理拆成 **6 个领域 Agent + 1 条六步闭环**。

**6 个领域 Agent**（对应数据治理的六大职能）：

| Agent | 职责 |
|-------|------|
| 资产 Agent | 自动盘点数据资产，建立资产目录与血缘 |
| 质量 Agent | 发现/诊断/修复数据质量问题（完整性、准确性、一致性、时效性） |
| 标准 Agent | 维护数据标准/指标口径，监控标准落地 |
| 主数据 Agent | 主数据识别、合并、去重、权威源仲裁 |
| 元数据 Agent | 技术/业务元数据采集与关联 |
| 生命周期 Agent | 数据分层存储、归档、销毁、冷热迁移 |

**六步闭环**：发现问题 → 智能诊断 → 给出建议 → 执行处置 → 验证效果 → 知识沉淀（回灌下一轮）。

**关键理念**：
- Agent 不是「代替人」，而是「人机协同（HITL）」——关键决策人兜底。
- 治理知识要显式沉淀（规则库/案例库），可被后续复用。
- 平台化：各 Agent 松耦合，靠共享知识层/调度层串联，而非单体。

### 1.2 文章二：阿里大数据根因定位 Agent 落地实践（工程蓝图）

**场景**：MaxCompute / Flink / Hologres / PAI 等计算平台的稳定性运维，目标「异常发现 →
降噪定界 → 根因定位 → 恢复」全闭环。

**四层架构**：

| 层 | 做法 | 关键算法/组件 |
|----|------|--------------|
| ① 异常发现 | 指标（单/多/分布）+ 日志 | RobustPeriod 周期分解 [SIGMOD]、深度学习多指标重构、SORN 分布异常检测 [KDD]；Flink 流式日志模板提取 + 语义聚类二次压缩（学术引用源自原文，**需核对原文确证**） |
| ② 降噪定界 | 大小模型融合分级 | 特征清晰→小模型直判；模糊/低置信→大模型 Agent 调下钻工具；输出 普通/黄灯/红灯 三级 |
| ③ 根因定位 Agent | **自进化闭环**（全文灵魂） | 知识图谱四要素 + 三阶段测评 + 运行时子图召回 |
| ④ 处置平台 | 统一入口串联全流程 | 算法检测 / 传统监控 / 人工上报三源汇入；可执行预案推送 + 平台内直接执行；钉钉卡片 + HITL 校准 |

**灵魂：根因 Agent 的自进化闭环**（分三块）

1. **知识图谱四要素（离线沉淀）**：

   ```
   原始工单 ──引用──> 根因空间 ──引用──> Skills ──引用──> Tools
   (历史案例)   (聚类+判重标准化)   (YAML定义)    (底层工具)
   ```

   - **根因空间**：把线上所有历史工单的根因，经「向量聚类 + 模型判重」归并成标准根因（c1/c2/c3…）。双重作用——既是测评骨架（知道 Agent 在哪些根因维度上弱），也是知识地图。
   - **Skill 合成**：标准根因 + 历史工单 + 可用 Tool → LLM 合成新 Skill → 相似度比对决定「新增 / 合并 / 丢弃」。
   - ⚠️ **Skill 是 YAML 结构化定义**（三阶段测评的合法性校验明确检查「结构 / 触发条件 / YAML 语法」），不是给人读的 Markdown。

2. **三阶段测评（上线闸门）**：

   | 阶段 | 检查内容 |
   |------|---------|
   | 合法性校验 | 结构 / 触发条件 / YAML 语法 |
   | 离线回放 | 根因覆盖率、Skills 覆盖率、根因分类准确率（人工校验标签的离线数据集） |
   | 线上灰度 | AB 测试；线上准确率、拦截率；与离线结果比对，找差距 → 数据飞轮 |

3. **运行时子图召回（最优雅设计）**：

   ```
   新工单 → 提取症状特征
          → 混合检索（BM25 关键词 + 向量语义，合并去重打分）
          → 沿引用网络召回 关联根因 / 技能 / 工具 小子图
          → 按相关性截断
          → 序列化为四段注入诊断 Agent：
              CASE  : 相似历史工单（症状 / 排查路径 / 处置结论）
              CAUSE : 候选根因  （定义 / 典型症状 / 反例边界）
              SKILL : 关联技能  （触发条件 / 步骤模板 / 输出格式）
              TOOL  : 工具清单  （签名 / 参数 / 适用条件）
   ```

   即「RAG-for-Agent」——不把所有 Skills 一股脑塞给 LLM，而是先检索相似历史案例，再沿引用网络精准召回一个小子图注入。

**Q&A 精华**：P0/P1 告警「聚合深度 vs 实时性」矛盾，阿里用「自顶向下（用户体感指标，少而精，立即定界）+ 自底向上（海量底层指标，大小模型降噪）」双轨解决。

### 1.3 文章三：AIOps 故障排障全流程（战术实战）

**场景**：电商平台三次深夜 P0 故障（数据库连接池耗尽 / 磁盘 IO 飙升 / JVM 内存泄漏）的复盘，演示 AI 如何把排查耗时从平均 45 分钟压到 5.7 分钟（提效 87.7%）。

**四层排障架构**（图8，全文核心）：

| 层 | 组件 |
|----|------|
| ① 数据采集层 | Prometheus 指标、Filebeat+ELK 应用日志、MySQL 慢查询日志、GitLab/Jenkins 部署变更事件 |
| ② AI 分析层 | 告警关联引擎（5min 窗口聚类）、日志模式匹配、部署关联引擎（Git Diff + 时间线） |
| ③ 知识层 | RAG 运维知识库（历史 Runbook）、Heap Dump 分析（大对象自动排序） |
| ④ 输出层 | 飞书/钉钉/企微根因报告推送、Grafana 故障时间线、自动工单 |

中枢是「根因推断引擎（因果推理链）」——整合 AI 分析层输出 + 知识层召回，生成根因结论并回灌知识层形成飞轮（思想与文章二自进化闭环同源，但粒度更粗：RAG 知识库 vs 知识图谱四要素）。

**AI 推理链路（案例1，图3）**：Prometheus 告警（连接池满）→ 慢查询日志聚合（3条>5s）→ 部署时间线关联（30min 前发版）→ Git Diff 分析（新代码批量 UPDATE 未加索引）→ 根因推断（全表扫描→占连接→池满）→ 修复方案（kill/回滚/加索引）。

**五大踩坑（全文最有实战价值的部分）**：

| # | 踩坑 | 本质教训 |
|---|------|---------|
| 1 | AI 误把「计划内月度报表任务」当异常慢查询风暴，建议紧急回滚——幸被人工拦截 | AI 不懂业务上下文；需白名单（SQL 打 `/* BATCH_JOB */`）+ 提供元信息（crontab/业务标签） |
| 2 | `jmap -dump` 触发 STW，在已卡死的服务上雪上加霜 | 重操作不能在用户正在用的 Pod 上做；改 `jcmd`（STW 缩短 70%）+ `HeapDumpBeforeFullGC` |
| 3 | 200 条原始告警 + 200 条 AI 分析 = 400 条消息淹没根因报告 | 缺降噪聚合；实现「时间窗口聚类→故障族→每族 1 条根因报告」（400→3 条） |
| 4 | 连接池泄漏检测阈值设 30s，致 20 天缓慢泄漏未被发现 | `leak-detection-threshold` = 最长预期 SQL × 3 |
| 5 | Caffeine 后台线程在容器化环境吃 CPU +15% | 指定独立线程池 `Executors.newFixedThreadPool(2)` |

**量化结论**：根因准确率 88%-95%（均值 91.7%），误判率 8.3%——「AI 是高级副驾驶，不是自动驾驶」。

> ⚠️ **场景局限**：技术栈为电商/JVM/中间件运维（HikariCP、Caffeine、jmap），与 powerelf（水利时序监测）差距大，**Heap Dump / 连接池 / 缓存等技术细节 0 可移植**；可借鉴的是方法论（报告格式 / 降噪 / 变更关联 / 踩坑防御）。

## 二、三篇文章的优点

### 文章一的优点

1. **领域 Agent 解耦清晰**：六大职能各自独立，按需启用，避免单体膨胀。
2. **闭环驱动持续治理**：六步闭环让治理从「一次性项目」变成「自我进化的平台」。
3. **HITL 理念贯穿**：强调人机协同、关键决策人兜底，避免全自动失控。

### 文章二的优点

1. **把「知识」工程化**：模糊的「经验」被拆成「工单 / 根因 / Skill / Tool」四类节点 +
   引用网络，可计算、可检索、可测评。
2. **子图召回 + 四段注入**：解决了「Skills 太多塞爆 LLM 上下文」的真实痛点，是
   RAG 思想在 Agent 领域的优雅落地。
3. **三阶段测评 = 上线质量闸门**：合法性 → 离线回放 → 线上灰度，每一步都有量化指标，
   避免「凭感觉上线」。
4. **大小模型分工**：清晰特征走小模型（快、便宜），模糊案例走大模型 Agent（准、贵），
   兼顾规模与成本。
5. **数据飞轮**：线上灰度结果回灌离线评测，形成越用越准的正循环。

### 文章三的优点

1. **案例具体、代码可复现**：每案例都有故障全貌表、SQL/代码修复对比、量化指标，是可照抄的模板而非空谈。
2. **踩坑诚实**：踩坑1（误判回滚）、踩坑3（告警风暴）是真实工程教训，作者没回避 AI 缺陷。
3. **AI vs 人工流程对照**：图2/图3 把每一步耗时拆解（聚合 30s→解读 1min→关联 30s），「提效从哪来」一目了然。
4. **「副驾驶而非自动驾驶」定位清晰**：反复强调 88-95% 准确率、必须人工验证，避免神化 AI。

### 共同优点

三篇都强调：**显式知识沉淀 + 闭环 + 人机协同**，这是 Agent 区别于「一次性脚本」的本质。

## 三、可借鉴的地方（对照 powerelf 现状）

| 借鉴要素 | 阿里/文章做法 | powerelf 现状 | 差距 / 借鉴点 |
|----------|--------------|--------------|--------------|
| **知识图谱四要素** | 工单→根因→Skill→Tool 建引用网络 | inspection 有 cases.json（**评测用例集**，非历史工单）+ rules/\*.md（类 Skill）+ 15 维度（**异常检测维度**，非根因空间）+ impl/ 可执行函数（类 Tool）；真实运行记录在 state/inspection_runs.jsonl | 四者散落各处，**未建引用网络** → 缺统一知识图谱中枢 |
| **Skill = YAML 结构化** | YAML 定义，可机器校验/回放 | rules 是给人读的 Markdown | 无法 lint / 无法回放，工程化不足 |
| **根因空间（聚类归并）** | 从历史案例聚类反推标准根因 | 15 维度是**检测维度**（检什么异常），根因层（为什么异常）缺失 | 需从真实案例分布聚类归并出标准根因，补上根因层 |
| **三阶段测评** | 合法性 → 离线回放 → 线上灰度 | inspection 已有 cases.json 评测 runner（≈ 离线回放）✅ | 缺①合法性 lint ③线上灰度 AB；根因/Skills 覆盖率指标值得引入 |
| **子图召回 + 四段注入** | 混合检索 + 子图召回 + 精准注入 | 各 skill 平铺，靠 LLM 自己匹配 rules | **单点最高 ROI 借鉴** |
| **大小模型融合定界** | 清晰→小模型；模糊→大模型 | 纯规则 + 单 LLM | 缺分流，规模上来后成本/延迟压力大 |
| **Skill 自进化闭环** | 工单→Wiki→skill 生成→回放→灰度 | inspection 有 rule-evolution + feedback-log.md（**设计了完整 schema 但当前 0 条记录，飞轮未启动**）⚠️ | 缺「自动从工单生成新 Skill」这一步；且需先让 feedback-log 积累真实 TP/FP/FN/TN 数据 |
| **领域 Agent 解耦**（文章一） | 六大领域 Agent 松耦合 | 5 个 skill 模块已松耦合 ✅，但无中央编排；且存在新旧目录并存（`chatbi/` ↔ `powerelf-chatbi`、`monitor/` ↔ `powerelf-monitor`、`early-warning/` ↔ `early-warning-v3/`；README 官方 Skills 表列 `powerelf-early-warning` 非 v3）⚠️ | 已具备解耦基础，缺知识共享层；Phase 2 抽共享层前需先定现行版；六大职能中「标准/主数据/元数据/生命周期」Agent 无对应模块，**属有意范围裁剪** |
| **HITL 拦截** | 阿里在「未来展望」才提 | early-warning-v3 已落地不可逆操作拦截（4cb72e3）✅ | **powerelf 已领先** |
| **六步闭环**（文章一） | 发现→诊断→建议→执行→验证→沉淀 | inspection 有发现→诊断→报告，但「沉淀回灌」弱 | feedback-log.md 需真正接入下一轮检测 |
| **结构化根因报告五段式**（文章三） | MTTR / 根因链 / 影响范围 / 修复措施 / 沉淀知识 | inspection/early-warning 有报告，格式不统一 | **直接采用五段式模板**，作所有模块报告统一规范——⭐⭐⭐（与 P1-3 优先级一致，成本极低、价值立现，但非战略级） |
| **告警时间窗聚类降噪**（文章三·踩坑3） | 5min 窗口把 200 条告警收敛成 3 条根因报告 | 无告警聚合；汛期告警可能成片 | 告警量大时必须；即文章二「降噪定界」层的战术落地 |
| **变更/操作关联**（文章三） | 关联 Git 提交 + 时间线，70% 故障与发版有关 | 无；水利无「代码发版」 | **水利版「变更」＝设备调试/参数修改/闸门调度/人工操作**——接入操作日志可大幅提升根因定位率 |
| **计划任务白名单**（文章三·踩坑1） | 计划内批量任务打标记让 AI 跳过 | inspection 有「季节/空闲护栏」雏形 ✅ | 汛期排涝/规律闸门启闭/灌溉放水 = 水利版「计划任务」，需白名单免误报 |
| **HITL 不可逆拦截 / 置信度评级**（文章三） | 踩坑1 误判回滚幸被人工拦截；强调准确率 88-95% 需人工验证 | early-warning-v3 已落地（4cb72e3）✅；inspection 有 `Ready/With caveats/Needs revision`、early-warning-v3 另有 `show/show_with_warning/suppress`（**两套未对齐，且 SKILL.md 文档标签与 report.py 代码标签漂移**）⚠️ | HITL 拦截 powerelf 已领先；置信度机制有但需统一——P1-3 报告模板前先对齐两套 |

**关键判断**：powerelf 与三篇文章面对的是**同构问题**——都是「海量时序指标/日志 → 异常 → 根因 → 处置」。
差别只在场景（阿里=计算集群运维，powerelf=水利工程监测）。因此可移植性高，
且 powerelf 在 **HITL 拦截** 一点已反超文章方案；**量化评测**仅在「离线回放」维度反超
（三阶段测评的「线上灰度 AB」仍缺，见 Phase 3），不可笼统称全面领先。

## 四、演进路线图

按「先验证、再抽离、后扩展」三阶段推进。每阶段都有可独立交付的产出，不赌大爆炸。

### Phase 1 — 近期（1~2 周）：验证子图召回最小可行（MVP）

在 **inspection** 单模块内闭环验证「子图召回 + 四段注入」，不动其他模块。

> 🛑 **前置盘点（Phase 1 启动前必做，2026-08-10 代码级核实）**
> - **语料量**：`inspection_runs.jsonl` 当前仅 **1 条**（2026-08-01 跑的一次）；cases.json 是 47 条构造评测用例，**不可当检索语料**。
>   → MVP 真实语料≈0。需先让 inspection 在真实库持续运行积累 runs（目标几十~上百条），否则实验结论不可信。
> - **根因层缺失**：inspection 输出的是**检测维度**（「水位连续上升」这类异常），**无「根因」概念**；
>   根因排序在 early-warning-v3（`topology.py` 的 causes 边）。子图召回四段中的 **CAUSE（候选根因）在 inspection 无对应物**。
>   → 要么先在 inspection 新增「根因输出」层，要么 MVP 跨模块引用 early-warning 的 `causal-rules.json`（与「单模块内闭环」冲突，需权衡）。
>   → 结论：Phase 1 的「单模块闭环」假设在 CAUSE 段上不成立，需在 MVP 设计阶段先决断根因来源。

- [ ] 把 inspection 现有 rules/\*.md（Skill）、15 维度（检测维度）、impl/ 可执行函数（Tool）、
      `state/inspection_runs.jsonl`（真实运行记录）显式建一张**引用关系表**（哪怕先是 JSON 手工维护）；
      cases.json 仅作评测集，不并入检索语料。
      > ⚠️ **已知语料匮乏**（2026-08-10 核实）：`inspection_runs.jsonl` 当前**仅 1 条**记录（2026-08-01 跑的一次）；
      > cases.json 是 47 条人工构造的成对评测用例。**子图召回 MVP 的真实历史语料目前≈0**——
      > 若不先让 inspection 在真实库持续运行积累 runs，MVP 只能在构造数据上跑，实验结论不可信。
- [ ] 实现一个 `retrieve_subgraph(symptom)`：BM25 + 向量相似度检索相似历史案例 →
      沿引用网络拉出关联根因/Skill/Tool。
- [ ] 把召回子图序列化为 CASE/CAUSE/SKILL/TOOL 四段，注入巡检 Agent 的诊断 Prompt。
- [ ] 对照 cases.json 评测 runner：注入前后的「误报率/漏报率/根因链率」变化，验证收益。

**交付物**：一篇实验报告（注入前 vs 注入后的指标对比）+ 一个可复用的 `retrieve_subgraph()`。

**退出标准（exit criteria）**：若注入后「误报率/漏报率/根因链率」任一核心指标无改善或劣化，
即判定子图召回在当前语料/规则形态下收益不成立，停止投入，仅沉淀实验报告与引用表设计，转向 P1 战术速赢项。

### Phase 2 — 中期（约 1 个月）：统一知识图谱中枢 + 测评补全

- [ ] **审 early-warning-v3 现有知识图谱实现**，评估能否抽成 `_shared/knowledge-graph/`
      跨模块共享层（inspection / early-warning / data-governance 共用根因空间与引用网络）。
- [ ] **Skill YAML 化**：把高频规则从 Markdown 升级为带 schema 的 YAML
      （触发条件 / 步骤模板 / 输出格式 / 关联根因 ID）。
- [ ] **合法性校验 lint**：YAML 规则的语法/结构/引用完整性检查，作为 cases.json 评测前的闸门。
- [ ] **补根因覆盖率 / Skills 覆盖率指标**：扩展 cases.json runner，量化「知识盲区」。
- [ ] **Skill 自进化雏形**：从 inspection feedback-log.md 的真实误报/漏报，半自动生成候选规则，
      人工确认后入库。

**交付物**：共享知识图谱层 + YAML 规范 + lint 工具 + 覆盖率报告。

**退出标准**：若 P0-1 评审结论为「物理拓扑耦合过深不可抽离」且自建语义引用网络收益未验证，
则 Phase 2 收缩为「仅 YAML 化 + lint + 覆盖率指标」（不建共享层），避免为共享而共享。

### Phase 3 — 远期（1~3 个月）：大小模型分流 + Agent 编排

- [ ] **大小模型分流**：清晰特征异常（如超阈值）走轻量规则/小模型直判；模糊/复合异常走
      大模型 Agent 调下钻工具。
- [ ] **Agent 编排框架**：参考阿里演进路径（Agent 平台 → LangGraph → 自研），
      powerelf 多步诊断可考虑引入 LangGraph 做状态机编排（替代当前「单次 LLM 调用」）。
- [ ] **线上灰度（AB）**：新规则上线走 AB，对比离线结果，启动数据飞轮。

**交付物**：分流调度器 + 多步诊断 Agent + 灰度发布通道。

**退出标准**：若 Phase 1/2 收益未达预期，P2 整体搁置（不提前投入基础设施）；灰度 AB 通道仅在
已有离线指标可对比、线上流量可划分时启动，否则保持人工审批上线。

## 五、当前急需做的点（按优先级）

> 聚焦最高 ROI，不贪多。

### 🔴 P0-1：审 early-warning-v3 知识图谱，拆成「物理拓扑复用」+「语义引用网络从零建」两问
这是后续所有工作的地基。先搞清楚现有知识图谱（git 4cb72e3：知识图谱建图 + 根因排序）的形态——
**已核实的已知事实**：图谱由 `build_topology.py` 建图脚本 + `analysis/topology-schema.sql` 建表，
数据落库为 `topo_node` / `topo_edge` 两张表（364 节点 + 832 边），`lib/topology.py` 仅做查询（爆炸半径
BFS / 故障团聚类 / 根因排序），**并非硬编码于单模块的 Python 结构，DB 表驱动的形态本身已具备共享前提**。
但注意：这是**物理拓扑**（测站/设备/测点/断面/大坝，用于爆炸半径），不是文章二的**语义引用网络**
（工单→根因→Skill→Tool，用于子图召回）。因此 P0-1 必须拆成两个子问题：

- **① 物理拓扑能否抽成共享层**：评估 `topo_node/topo_edge` + topology.py 能否迁到 `_shared/knowledge-graph/`
  供多模块共用——大概率可行，**若可抽离 Phase 2 直接起飞**。
  > ⚠️ 补注（2026-08-10 核实）：节点/边类型（4 种 belongs_to/upstream_of/causes/near）、
  > 空间阈值（`UPSTREAM_MAX_DISTANCE_KM=10.0`、`NEAR_STATION_MAX_DISTANCE_KM=1.0`）、
  > 根因排序 5 权重（temporal_priority 0.25 / topology_centrality 0.20 / causal_evidence 0.25 /
  > alarm_severity 0.15 / historical_recurrence 0.15）**均为硬编码常量**，仅 causes 边规则可配置；
  > 共享前需将水利特定常量参数化。
- **② 语义引用网络需从零建**：inspection / early-warning / data-governance 的「工单→根因→Skill→Tool」
  引用网络当前不存在，与物理拓扑数据模型、用途都不同，**不能靠抽物理拓扑获得**，需单独设计节点/边 schema。
  > ⚠️ 补充障碍（2026-08-10 核实）：语义网络的「根因」节点在 inspection 当前**无对应物**——inspection 只有
  > 15 个**检测维度**（检什么异常），不输出「为什么异常」的根因；根因排序仅存于 early-warning-v3。
  > 故 P0-2 子图召回的 CAUSE 段，要么跨模块借 early-warning 根因（破坏单模块闭环），要么 inspection 先补根因层。

**结论**：若 ① 可抽离，Phase 2 直接起飞；若不可抽离，先在 Phase 1 单模块内自建引用表。
② 无论如何都要在 Phase 1 起步（P0-2 已覆盖），不能等 ① 的结果。

### 🔴 P0-2：在 inspection 做子图召回 MVP（Phase 1 全部）
单点最高价值。**语料定位先分清**：cases.json 是**评测用例集**（人工构造的成对正反例，规模小），
适合当效果对照的评测集，**不适合当检索知识库**；真实检索语料应来自
**`state/inspection_runs.jsonl`（真实巡检运行记录）与 monitor 原始告警**。
> ⚠️ **已知答案（2026-08-10 核实）**：`inspection_runs.jsonl` 当前**仅 1 条**记录。
> 「先盘点真实历史案例量」的盘点结果已出：**语料≈0**。MVP 的真实前提动作不是「决定检索方式」，
> 而是**先积累语料**——让 inspection 在真实库持续运行，或确认 monitor 原始告警有可用历史存量。
> 在此之前，BM25/向量的选型无意义（无可检索数据）。

无需等共享层，一篇实验报告即可决策后续投入。

### 🟡 P1-1：规则 YAML 化 + 合法性 lint
低成本、高收益。让规则从「给人看的文档」变成「可校验、可回放、可纳入覆盖率统计的结构」。
接入 cases.json 评测前作为语法闸门。

### 🟡 P1-2：根因覆盖率 / Skills 覆盖率指标
扩展现有 cases.json runner，量化「知识盲区」，为规则演进提供数据驱动依据。

### 🟡 P1-3：根因报告五段式模板 + 告警时间窗聚类（文章三战术速赢）
文章三给的全是**战术级速赢**（立即可做、成本低、收益直接可见），与 P0 的战略级补强互补：
- **根因报告五段式模板**（MTTR / 根因链 / 影响范围 / 修复措施 / 沉淀知识）——跨 inspection / early-warning /
  data-governance 统一。成本极低，价值立现。
- **告警时间窗口聚类**——应对汛期告警成片，把 monitor 原始告警按 5min 窗口聚合成「故障族」，每族出 1 条根因报告。
- **水利版变更关联**——识别并关联「设备调试 / 参数修改 / 闸门调度 / 人工操作」与故障时间线（水利的「发版后 30min 70% 相关」类比）。
  ⚠️ **前置盘点**：先确认上述操作日志在 monitor / early-warning / 设备系统**是否已有数据源**（表/API/流水）；
  若仅有现场纸质记录，则先建轻量人工登记通道，再谈自动关联——不要先建引擎后找数据。

### 🟢 P2：大小模型分流、Agent 编排、线上灰度
等 Phase 1/2 验证收益后再上，避免过早投入基础设施。

## 六、一句话结论

> 运行时精准召回注入」（文章二），战术上可立即落地「报告五段式 + 告警降噪 + 变更关联」（文章三）。**
