# 智能巡检运行分析报告与优化方案

> 文档生成时间：2026-08-13
> 关联仓库：powerelf-skills（`powerelf-inspection` / `powerelf-data-governance` / `powerelf-monitor`）
> 触发背景：对全设备执行近 7 天智能巡检后，发现报告存在"离线设备数异常偏多、MAD 统计表只显 4 维、渗压变化率 507 次却标正常、水位 MAD 异常率 21.6%、报告前后不一致"等问题，本文记录根因分析与优化方案。

---

## 1. 巡检检测机制现状

### 1.1 工具链分层

| 层 | 工具 | 作用 | 窗口 |
|---|---|---|---|
| 巡检主引擎 | `powerelf-inspection/impl/inspection_analyzer.py` | 15 维度异常检测 + 5 层判定 + 自动诊断 | 用户指定 `--days`（本次 7 天） |
| 巡检业务 | `powerelf-inspection/impl/inspection_tool.py` | 质量评分 / 缺陷预测 / 路线优化 | 自定义起止 |
| 离线检测（台账） | `powerelf-data-governance/scripts/classify_offline_by_duration.py` | 批量离线分级（台账 status + 离线记录表） | **无时间窗口**（全历史） |
| 离线检测（新鲜度） | `powerelf-data-governance/impl/offline_detector.py` | 按 `MAX(tm)` 距今是否超阈值推断离线 | 实时（当前时刻） |
| MAD 统计 | `powerelf-data-governance/impl/anomaly_detector.py` | MAD / IQR / 百分位异常检测 | 默认 30 天 |
| 报告渲染 | `powerelf-inspection/impl/inspection_analyzer.py::generate_report` | Markdown 模板渲染（`references/report-template.md`） | — |

### 1.2 15 分析维度（inspection_analyzer）

水库水情、雨量、渗压、渗流、GNSS 位移、闸门、泵站、水质、墒情、白蚁、巡检结果、设备状态、告警、MAD 统计异常、多指标关联异常。

### 1.3 5 层异常判定体系

```
第1层: 阈值判定（绝对越限）→ 第2层: 变化率检测（突变）
  → 第3层: 趋势检测（单向持续）→ 第4层: MAD统计异常（离群）
  → 第5层: 多指标关联（矛盾分析 → CRITICAL）
```

## 2. 模拟数据构造（simulate_7d_data.py）

### 2.1 设计目标

1. 数据量符合真实情况（按实际采集频率：监测表每小时 1 条、GNSS 每日 1 条、水质每日 2 条、墒情每小时 1 条、白蚁每周 1 条、巡检任务每日 4 条、告警每日 2 条）
2. 大部分设备正常，仅有小幅随机波动（不触发检出阈值）
3. 构造 3~5 台问题设备，其中 1~2 台严重，其余中等/细微

### 2.2 问题设备方案（方案 A，5 台）

|---|---|---|---|
| 🔴 严重① | 渗压计 eq_id=139 (测站93) | 最后 6 点连续上升 455→472kPa | 突变 17.1kPa WARNING + MAD z=57.6 WARNING |
| 🔴 严重② | GNSS eq_id=155 (测站97) | 速率 1.2mm/d + 累计位移 12mm | CRITICAL + WARNING |
| 🟡 中等① | 泵站 eq_id=131 (测站89) | 三相电流 50/62/38A 不平衡 24% | WARNING |
| 🟡 中等② | 闸门 eq_id=132 (测站90) | 开度单步 1.18→2.50m 突变 | WARNING |
| 🟢 细微 | 雨量 eq_id=127 (测站85) | 单时段 35mm 短时强降雨 | WARNING + 蓝色预警 INFO |

### 2.3 正常设备波动设计（防误报）

- 水位：短周期（6 点）正弦 + 噪声，围绕基线 461.5m，末端回落，连续单调 ≤4 点
- 渗压：按 st_id 派生统一基线（430-460kPa），噪声 ±0.3kPa
- GNSS：纯噪声 ±0.02mm/d，末端回落
- 各维度波动幅度均低于检出阈值（水位连续上升需 5 点、渗压突变需 >5kPa、闸门突变需 >1m、泵站不平衡需 >10%）

- 先清理近 7 天窗口内旧数据（含 `eq_code='MOCK'` 恒值），再插入模拟数据
- 全部走 `_shared/lib/db.py` 连接，事务提交

## 4. 报告问题与根因分析

### 4.1 问题 1：设备离线数异常偏多（524 台记录 vs 54/128 设备）

**报告表现**：

| 离线等级 | 设备数 | 说明 |
|---|---|---|
| CRITICAL | 84 台 | 严重离线 >24h |
| ERROR | 158 台 | 长期离线 4-24h |
| WARNING | 161 台 | 短期离线 1-4h |
| INFO | 121 台 | 轻度离线 <1h |

总离线 524 台记录，同时标注"设备离线率 42.2% (54/128)"。

**根因（三层叠加）**：

1. **检测范围超 7 天**：`classify_offline_by_duration.py` 查询 `eq_equip_base.status=0` LEFT JOIN `eq_equip_offline_record`，**无任何时间窗口过滤**，5-6 月的历史离线记录全部计入；
2. **记录数 ≠ 设备数**：LEFT JOIN 将"1 台设备的多条离线记录"展开成多行（实测 586 条记录仅涉及 67 台设备），报告把"记录数"写成"台数"；
3. **累计时长分级**：按 `total_offline_duration`（全生命周期累计）分级，76 天前的存量离线被当成"当前严重问题"放大展示。

**结论**：42.2% (54/128) 是 `eq_equip_base` 台账**真实现状**（非模拟数据问题）；524 是离线**事件记录数**，两个口径混用导致"几十台变几百台"的错觉。

### 4.2 问题 2：MAD 统计表只显 4 维

**根因**：MAD 统计表来自 **data-governance 的 `anomaly_detector.py`**，它只支持 4 张核心监测表（`st_rsvr_r` / `st_pptn_r` / `st_pressure_r` / `st_percolation_r`），而 inspection 的 15 维是另一套工具（`inspection_analyzer.py`）。报告把两套工具的输出拼在一起，MAD 表天然只有 4 维，并非"15 维中只显示了 4 维"。

### 4.3 问题 3：渗压"变化率 507 次"却标"数据分布正常"

**根因**：`anomaly_detector.py` 是**全表整体检测**（不分设备），把 23 台渗压计混在一起按 tm 排序；模拟数据给每台设备设了不同基线（430~460kPa 不等），相邻时刻两条记录若来自不同基线设备 → 变化率突跳 → **507 次"变化率超限"是基线混排造成的误报**。MAD 用全表中位数（≈447）衡量，波动被平滑 → 0 异常。

对比：inspection 的 analyzer **按 st_id 分组**检测，正确检出了渗压计 93 的 17kPa 突变（报告 F003/F004 的来源）——所以"渗压有问题"在巡检工具里存在，只是 MAD 统计表（data-governance 工具）没显示。

### 4.4 问题 4：水位 MAD 21.6% / 雨量 19% 异常率虚高

**根因**：近 30 天窗口内残留 **1,080 条 rz≈786m 的旧 MOCK 水位**（2026-07-14 ~ 08-06）和 **1,740 条 p=60mm 的旧 MOCK 雨量**（7-30 天窗口）。模拟程序 `_delete_window` 只清理了近 **7 天**的 MOCK，7~30 天窗口的旧 MOCK 没清；`anomaly_detector` 默认 30 天窗口 → 把 786m/60mm 的旧恒值算进 MAD → 异常率虚高。

**结论**：数据清理范围不够（应清 30 天或全部 `eq_code='MOCK'`），不是正常设备本身被造出异常。

### 4.5 问题 5：报告前后不一致（4 处）

| # | 不一致 | 实况 |
|---|---|---|
| 1 | "已知局限：水质/墒情/白蚁/巡检任务无数据" | 4 表当前实有 42/168/7/28 行——报告是增强数据前生成的旧版（或命中 5 分钟 workflow 缓存），需重跑 |
| 2 | "总离线设备 524 台记录" vs "42.2% (54/128)" | 记录数 vs 设备数口径混用，且 524≠586（报告数字与库内实测也对不上） |
| 3 | MAD 表数据点（1491/1672/3841/334） | 与 30 天实测（2976/3532/3887/338）不一致——报告生成时的窗口/参数不可复现 |
| 4 | "渗压变化率 507 次"却标注"数据分布正常" | 表述自相矛盾，且 507 次是基线混排误报，非真实异常 |

### 4.6 各工具窗口一览（混淆根源）

| 工具 | 默认窗口 | 与用户"近 7 天"问话的关系 |
|---|---|---|
| inspection_analyzer | `--days`（用户指定 7） | ✅ 一致 |
| anomaly_detector（MAD） | 30 天 | ❌ 超出 |
| classify_offline_by_duration | 全历史（无窗口） | ❌ 严重超出 |
| offline_detector（新鲜度） | 实时当前时刻 | ⚠️ 不同语义（时刻 vs 周期） |

## 5. 时间范围口径问题的解决方案

### 5.1 问题本质

用户问话是"查近 7 天数据"，但实际覆盖范围有 30 天（MAD 检测）甚至全历史（离线检测），造成汇总口径混乱。**两种极端方案都不可行**：

| 方案 | 问题 |
|---|---|
| A. 所有检测强加近 7 天限制 | 方法学上做不到：MAD 需 `min_samples=20`（GNSS 每日 1 条 → 7 天仅 7 点，无法检测）；白蚁每周 1 次（7 天可能 0~1 条）；缺陷预测需 6 个月历史；离线是累积事实（截断会丢失"已离线 76 天"的严重性） |
| B. 仅在各章节标注时间范围 | 无一致性约束时，读者容易把 30 天窗口的异常误当"近 7 天新发生"，把全历史离线记录误当"当前离线设备数"——正是本次报告混淆的根源 |

### 5.2 推荐方案：B 为主 + A 的一致性约束（三层）

```
第1层 报告头部统一声明（一次讲清）
  "本次巡检观测窗口：近 7 天（2026-08-06 ~ 08-13）。
   MAD/统计类检测以近 30 天为历史基线（仅作判定依据，不参与计数）；
   设备离线为窗口内口径（见第 6 节三口径分层，不截断全历史）。"

第2层 每个章节标题下标注本节窗口
  ## 渗压监测（观测窗口：近7天；MAD基线：近30天）
  ## 设备状态（口径分层：快照/窗口内新增/窗口内活跃度）

第3层 硬约束：汇总计数口径统一
  所有"异常 N 项 / CRITICAL N / WARNING N"一律按观测窗口（7 天）统计；
  跨窗口信息只允许出现在"判定依据/背景"位置，不得混入计数，且必须单独标注。
```

**为什么这是最优解**：
- 保住检测能力（MAD 有 30 天基线、离线保留累积严重性、缺陷预测有 6 个月历史）
- 消除混淆（用户问"7 天"得到的汇总数字就真的是 7 天口径）
- 可对账（汇总计数统一 → "异常 N 项"与明细能对上）

## 6. 离线检测机制与优化方案

### 6.1 当前 skill 的离线判定双路径

| 路径 | 判据 | 代码位置 | 对应语义 |
|---|---|---|---|
| 台账状态直判 | `eq_equip_base.status = 0` 即离线 | `classify_offline_by_duration.py`（批量分级）、inspection `analyze_equipment` | "有状态且状态为离线，直接判断" |
| 数据新鲜度推断 | 该表 `MAX(tm)` 距今 > 阈值 → 判离线 | `offline_detector.py`：`deadline = latest + threshold 分钟`，`deadline < now → OFFLINE` | "周期内始终没数据 → 推断离线" |

新鲜度路径判定核心（`lib/offline.py::determine_status`）：
```
deadline = MAX(tm) + 阈值(分钟)
deadline < now  → OFFLINE（这个周期内没来过数据）
否则           → ONLINE
```

### 6.2 阈值配置存在但未生效（关键发现）

库里**有两张配置表**，确实按设备类型配了不同周期：

| 配置来源 | 实际内容（2026-08-13 查库） | 是否被代码读取 |
|---|---|---|
| `dg_equip_offline`（按站类型） | SP=360min、GN=60、PP/DP/DD=120、RR/ZZ=60、YZ=0… | ❌ `offline_detector.py` 没读这张表 |
| `eq_business_equip_relation.offline_threshold/frequency` | 全部 frequency=60、offline_threshold=0 | ❌ 只被 SELECT 展示，不参与判定 |

`offline_detector.py` 实际用**硬编码兜底**：
```python
DEFAULT_THRESHOLDS = {"SP": 360, "GN": 60, "PP": 60, "DP": 60, "DD": 60, "YZ": 60, ...}
threshold = DEFAULT_THRESHOLDS.get(table, 60)   # ← 键是站类型，查的却是表名！
```
键是站类型代码（SP/GN/…），`get(table, 60)` 传的是**表名**（如 `st_rsvr_r`）——键永远对不上，**实际全部 fallback 到 60 分钟兜底**。"SP 水位 360 分钟"配置从未真正生效。这解释了"大量渗压计离线 76 天"：渗压（YZ）真实阈值应为 0（不检测）或配置值，但统一按 60 分钟判 → 5 月断数后全部落入"离线"。

### 6.3 "全生命周期口径"不可取的论证（离线率应有参考意义）

单纯"7 天 + 30 天两个离线率并列"会得到**两个相同数字**（实测：离线记录∩窗口 60/60、status 快照 42.2%/42.2%），因为：
- 所有离线记录都是历史存量（最早 2025-11-19，近 30 天无新增）
- `eq_equip_base.status` 是快照，不随窗口变化
- 唯一真实随窗口变化的量是"数据新鲜度"（表 MAX(tm) 距今）

### 6.4 推荐方案：三口径分层（不按窗口并列，按语义分层）

| 口径 | 回答的问题 | 计算方式 | 时间语义 |
|---|---|---|---|
| **A. 当前快照** | 现在有多少台设备是离线的？ | `eq_equip_base.status=0` | 与窗口无关（此刻状态，实时计算） |
| **B. 窗口内新增** | 本次巡检周期内新发生了几次离线？ | `offline_start_time` 落在窗口内 | 跟随用户查询窗口（7天/30天） |
| **C. 窗口内活跃度** | 本次巡检周期内哪些设备没在产数据？ | 各监测表窗口内 `COUNT(DISTINCT eq_id)` / 映射设备数 | 跟随用户查询窗口 |

报告呈现示例：
```
## 设备状态（口径分层）

| 口径 | 数值 | 时间语义 |
|---|---|---|
| 当前快照 | 离线 54/128 (42.2%) | 此刻台账状态 |
| 窗口内新增离线 | 0 次 | 近7天新发生 |
| 窗口内数据活跃度 | 7/7 表 100% | 近7天有数据设备/映射设备 |
```

配套纪律：
1. 窗口跟随用户查询：`--days N` 决定 B/C 的窗口，A 永远当前
2. 不混口径：汇总计数只统计"窗口内"（B+C），快照（A）单独列
3. 存量标注起止：对 B 命中的长期离线记录，标注"自 2026-05-20 起离线"而非累计时长
4. 42.2% 是**实时计算**的（每次运行查 `eq_equip_base.status`），不是常量

### 6.5 离线检测落地改造点（待实施）

1. `offline_detector.py`：改为真正从 `dg_equip_offline` 按 `st_type` 读阈值（通过 `eq_business_equip_relation.st_type` 关联），SP=360/PP=120/YZ=0 等配置才生效
2. 修复 `DEFAULT_THRESHOLDS.get(table, 60)` 键不匹配问题（键应为表名或显式传 st_type）
3. 让"新鲜度推断"结果与台账状态路径打通，两条路径合一
4. `classify_offline_by_duration.py` 增加 `--days` 参数，支持窗口内新增（B）统计

## 7. 报告详细度与图表增强方案

### 7.1 现状

- 报告为纯 Markdown 模板渲染（`references/report-template.md` + `lib/report.py`），**无任何图表**
- 模板支持占位符渲染（`generated_at` / `run_id` / `days` / `dim_count` / `critical` / `warnings` / `ok_count` / `sections` / `recommendations` / `data_notes` / `qa_checklist`）
- 环境已具备 `matplotlib 3.11.1`，可直接生成图表

### 7.2 增强项清单

| 增强点 | 做法 | 输出 |
|---|---|---|
| 逐维度趋势图 | 水位/渗压/渗流/位移近 7 天时序曲线 + 异常点标注 | matplotlib 生成 PNG，报告嵌入 |
| 异常分布图 | 各维度异常数柱状图、severity 饼图 | PNG |
| 离线全景图 | 离线分级条形图（区分"设备数"与"记录数"双口径） | PNG |
| 关联分析图 | 水位-渗压双轴联动曲线（对应 F003/F005 耦合结论） | PNG |
| 口径修正 | 离线表拆分"设备数/记录数"两列，MAD 表注明窗口与分组方式 | 表格 |
| 窗口声明 | 头部统一声明 + 每章节标注观测窗口（见第 5 节） | 文本 |

### 7.3 报告结构建议（增强后）

```
# 智能巡检报告
- 头部：观测窗口声明（第5节第1层）
- 一、异常汇总（severity 表格 + 分布图）

- 三、设备状态（三口径分层表，第6.4节）
- 四、根因分析（自动诊断链结果）

- 七、附录：数据覆盖清单（各表窗口内行数，防"无数据"误判）
```
