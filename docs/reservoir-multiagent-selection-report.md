## 【内容摘要】

针对数字孪生水库"1个调度主管 + 6类专业子Agent"多智能体集群建设,现有两种技术路径可选:

- **方案A**:基于 **LangGraph** 自建多Agent集群(独立 Python + 状态图编排);
- **方案B**:基于现有 **Hermes 智能体平台 + Skill 体系**,以"领域 Skill + 薄编排层"实现。

> 关于大模型:本汇报将"具体采用何种模型"视为**可配置的建议项,而非选型的决定性因素**。本地私有化部署是应满足的约束,但模型规格(参数量、是否混合云端)可按需调整,详见第六节"大模型选型建议"。

经多维度对比分析,**建议采用方案B**。决定性理由(均基于架构层面,与模型无关):

1. **系统的复杂度大头在水利领域规则,而非工作流机制**——水情感知、大坝安全、设备运维、调度规程等领域逻辑是本系统的本质难点;方案B 已将这些规则编码为现成 Skill 与共享算法,方案A 则需将其整体移植进图节点,属纯重复投入。
2. **自进化、评测、安全、可观测为方案B 的平台原生能力**——方案A 需从零构建上述全部能力。
3. **方案B 唯一的真实短板(无原生工作流引擎)可被一层薄确定性编排关闭**;而方案A 的短板(重建平台能力 + 移植领域资产 + 新增独立服务运维)更大且不可绕过。

需要客观指出:在剥离模型因素后,**方案A 的竞争力较此前评估有所上升**——其工作流引擎、检查点/断点续跑、人机协同、多分支回放等确为成熟强项,契合防汛闭环的 resumable 需求;但其整体仍逊于方案B,原因如上三条。详细对比与依据见正文第四至第七节。

## 一、汇报背景与目标

### (一)业务背景

数字孪生水库建设要求实现"感知—研判—推演—决策—归档"全链路自主智能闭环,覆盖汛期防汛调度、大坝安全诊断、日常精细化管控等场景。传统模式下,水文、大坝、雨情、库容、泄洪设备数据分散,仿真推演与调度决策相互割裂,亟需一套多智能体协同体系承担全链路自动化。

### (二)技术选型问题

在"如何实现多Agent集群"这一工程问题上,存在两条技术路线,其架构范式、能力假设、建设成本差异显著,需在立项前予以明确,避免方向性返工。本汇报即针对该选型问题展开对比并给出建议。

### (三)汇报目标

明确多Agent集群的技术底座与编排范式,为后续立项、资源投入、实施排期提供决策依据。

## 二、我方当前技术方案详述

> 本节详细说明我方既已建成并在运行的智能体技术方案。这是本次选型最重要的现实前提——任何新方案都应以此为基础增量演进,而非另起炉灶。

### (一)总体设计理念

我方现行 `powerelf-skills` 体系遵循四项设计理念(v2 架构):

1. **规则内嵌**:核心算法与判断规则直接写入 Skill,智能体可独立判断,不依赖外部平台接口;
2. **按需加载**:轻量入口 + 模块化规则文件,按用户意图动态加载,显著降低资源消耗;
3. **自我进化**:每个 Skill 内含可调参数表与反馈日志,支持参数与规则的持续优化;
4. **高可扩展**:新增规则仅需添加 `.md` 文件,无需改动既有结构。

### (二)体系构成

仓库为 **monorepo** 形态,由 **5 个领域 Skill + 1 个跨 Skill 共享层(`_shared`)** 组成:

| Skill | 规则规模 | 核心能力 |
|-------|----------|----------|
| `powerelf-monitor` | 5规则+3算法 | 12类监测:水库/河道/闸站/潮汐/雨情/闸门/泵站/GNSS/渗流/渗压/墒情/白蚁 |
| `powerelf-early-warning` | 5规则+3策略 | 阈值/开关量/状态变化/大坝/趋势预警,视频AI报警,通知分发 |
| `powerelf-inspection` | 10规则+2模式 | 智能巡检、异常判定、缺陷分类、设备状态、质量评估、任务生命周期等 |
| `powerelf-chatbi` | 3规则 | 意图分类、图表选择、SQL生成(覆盖20+业务表) |
| `powerelf-data-governance` | 5规则+3算法 | 缺失检测、MAD异常检测、智能插值、离线监测、统计评分 |

`_shared` 共享层作为**单一事实源**,统一提供数据库连接、表结构定义、共享算法、共享规则、鉴权约定与进化模板,避免各 Skill 各自维护导致的不一致。

### (三)分层加载机制(资源经济)

采用四级分层按需加载,严格控制资源开销:

| 层级 | 内容量级 | 内容 |
|------|----------|------|
| Level 0 | ~300 token | 入口索引,仅列出 Skill 名称 |
| Level 1 | ~500 token | Skill 入口,能力概览 + 加载指令 |
| Level 2 | ~1000–2000 token | 规则模块,具体判断逻辑 |
| Level 3 | ~1500–3000 token | 算法详解 / 接口参考 |

即:无意图时仅加载 Level 0;命中某 Skill 后逐级下沉,无关内容不进入上下文。

### (四)数据访问与安全约束

- **统一数据访问**:`_shared/lib/db.py` 提供 `columns()` 与 `COLUMN_MEANINGS`,从机制上杜绝"大模型臆测列名"这一误报根因——所有取数须经结构化列查询,而非自由生成;
- **安全护栏**:`_shared/hooks` 强制屏蔽裸数据库连接,所有访问必须经由安全路径;`_shared/api-auth.md` 统一 REST 鉴权约定。

### (五)自我进化机制(平台原生)

- **参数化与反馈**:每个 Skill 的 `evolution/` 目录包含 `parameters.md`(可调参数注册表:当前值、合理范围、调整依据)与 `feedback-log.md`(执行反馈日志:事件、原因、改进措施);
- **自动优化闭环**:平台层提供 `autoresearch` 能力,可"自动反复运行某 Skill、按二元评测打分、变异提示词并保留改进",构成无需人工介入的自优化回路。

### (六)评测体系(平台原生)

各 Skill 配套 `autoresearch/eval_cases/cases.json` 与评测脚本(如 `eval_runner.py`),已落地**误报率、漏报率、根因链率**等量化指标,任何规则或参数调整均可回归验证。

### (七)运行平台

- **Hermes 智能体平台**:现行 Skill 运行环境,提供 Skill 路由、状态记录与运行时可观测;
- **DeerFlow 2.0**(开源,已部署于本机 `/opt/git/deer-flow`):面向"子Agent + 记忆 + 沙箱"的超级智能体框架,原生支持动态工作流,适用于多方案并行推演、自进化扫参等场景。

### (八)典型请求流转

一次典型研判请求在现行体系中的流转路径为:

```
用户意图
  → Hermes 路由(命中目标 Skill)
  → 按需加载入口(Level 1)→ 按需下沉规则/算法(Level 2/3)
  → 经 db.py 安全取数 + 确定性算法研判
  → 结构化结论 + 自然语言组织输出
  → 执行反馈写入 evolution/feedback-log.md
  → 周期性评测 / autoresearch 自动优化
```

> 小结:我方既已建成"规则内嵌 + 按需加载 + 自我进化 + 评测闭环"的完整智能体体系,5 个领域 Skill 覆盖监测、预警、巡检、取数、治理,并具备平台级安全与可观测能力。本集群建设中,6 类子 Agent 至少 3 类(水情感知、大坝安全、设备运维)可直接复用现有 Skill,共享层可全量复用。这是选型必须正视的现实基础。

## 三、候选方案概述

### (一)方案A:基于 LangGraph 自建多Agent集群

以 LangGraph 为编排内核,构建"1张主图(主管调度)+ 6张子图(专业Agent)"。每个专业Agent为独立 Subgraph,具备自身的"思考—工具—循环"能力;主管节点动态选择下一执行Agent,通过条件路由实现串行、并行、重试与终止,配合持久化检查点实现断点续跑。

**核心范式**:智能 = 大模型推理循环;编排 = 自维护的状态图代码。

### (二)方案B:基于 Hermes + Skill + 薄编排层

将6类子Agent实现为**领域 Skill**(规则 + 算法 + Python 实现 + 评测 + 进化参数),复用现有 Skill 与共享层;新增一个**主管调度 Skill**,其内部以一层**轻量确定性编排**(显式有向无环图 DAG + 分支规则 + 状态文件)承担闭环时序、断点续跑与结果仲裁;在需要"多方案并行推演对比""自进化扫参"时,按需调用 DeerFlow 动态工作流。

**核心范式**:智能 = 内嵌规则与确定性算法;大模型承担路由与表述;编排 = 平台 + 一层薄 DAG。

## 四、多维度对比分析

| 对比维度 | 方案A(LangGraph 集群) | 方案B(Hermes + Skill + 薄编排) | 评估结论 |
|----------|------------------------|----------------------------------|----------|
| **智能载体** | 大模型推理循环(每节点 think-act) | 确定性规则 + 算法,大模型仅路由/表述 | 方案B更可靠可审计 |
| **编排引擎** | 自行编写并维护 StateGraph、条件边、检查点 | 平台提供路由/状态,主管 Skill 内置薄 DAG | 方案B运维更轻;方案A原生更完整 |
| **状态与断点续跑** | 成熟,原生支持检查点/恢复 | 薄 DAG + 状态文件实现,需自管正确性 | **方案A占优** |
| **人机协同(HITL)** | 原生中断/恢复机制成熟 | 需在薄编排层实现人审门 | 方案A略占优,方案B可补齐 |
| **多方案并行推演** | 原生分支与回放 | 按需调用 DeerFlow 动态工作流 | 方案A原生略优,方案B可补齐 |
| **自进化能力** | 无,需从零构建 | 平台原生(autoresearch + evolution/) | **方案B显著占优** |
| **评测体系** | 无,需从零构建 | 各 Skill 已有 cases.json 与评测脚本 | **方案B显著占优** |
| **安全合规** | 需自建 | 既有(db.py 安全路径、连接屏蔽、鉴权约定) | **方案B占优** |
| **可观测性** | 需自建 | 既有(反馈日志、路由记录、评测输出) | 方案B占优 |
| **既有资产复用** | 无法原生复用,需移植 | 3/6 子Agent现成,共享层全复用 | **方案B显著占优(关键项)** |
| **领域复杂度承载** | 领域规则须移植进图节点 | 领域规则已编码为 Skill | **方案B显著占优(关键项)** |
| **资源消耗** | 每轮闭环多次全量大模型调用 | 分层按需加载,大模型仅在必要节点触发 | 方案B占优 |
| **运维负担** | 新增一套需部署/监控/升级的服务 | 复用现有平台,无新增重型服务 | 方案B占优 |
| **规则迭代成本** | 改图、重测、重部署 | 增删 `.md` 规则文件即可 | 方案B占优 |

> 综合判断:方案A 在"状态断点续跑、人机协同、多方案并行"三项工作流原生能力上占优;但在"自进化、评测、安全、可观测、资产复用、领域复杂度承载"等更关乎系统本质的维度上,方案B 占优或显著占优。其中**"既有资产复用"与"领域复杂度承载"为本系统的关键项**——复杂度集中于水利领域规则,而该部分方案B 已具备、方案A 需重建。方案A 的工作流优势可通过方案B 的薄编排层与 DeerFlow 予以补齐,反之则不然。

## 五、优劣势分析

### (一)方案A 优势

1. **控制流默认可审计、可复算**:编译后的状态图为一等制品,可可视化、可对"给定输入必走某节点序列"进行单元测试;
2. **断点续跑与人机协同成熟**:检查点机制与中断/恢复为长流程量身设计,契合防汛连续过程;
3. **多分支与回放**:支持从任意检查点回放、并行多时间线,便于多方案对比;
4. **框架生态成熟**:重试、兜底、超时、熔断等有现成模式。

### (二)方案A 劣势

1. **无法原生复用既有领域资产**,规则、算法、评测用例均需移植进图节点;
2. **需从零构建自进化、评测、安全、可观测等平台级能力**,与既有体系重复建设;
3. **新增一套需独立部署、监控、升级的服务**,运维成本高;
4. **规则迭代成本高**,改动需修改编排代码并重新测试部署;
5. **领域复杂度被强行装入工作流框架**,主次倒置(本系统难点在领域规则,而非工作流机制)。

### (三)方案B 优势

1. **直接复用3/6现成子Agent与全部共享层**,建设成本低、周期短;
2. **自进化、评测、安全、可观测均为平台既有能力**,开箱即用;
3. **领域规则已编码为 Skill**,新增规则仅需添加文件,迭代便捷;
4. **资源经济、运维轻量**,无新增重型服务;
5. **对小模型规格更宽容**(大模型只做路由/表述),模型选型灵活、成本可控。

### (四)方案B 劣势(需正视并弥补)

1. **无原生工作流引擎**:可恢复的多步闭环、检查点、多方案分支需在主管 Skill 中以薄 DAG 自行实现,正确性、断点语义需自管;
2. **跨 Skill 状态共享为隐式**:Skill 间状态经文件/数据库/约定传递,需在主管层显式约定结构化状态;
3. **并行/fan-out 非一等原语**:需借助 DeerFlow 动态工作流补齐;
4. **框架级保障(重试/超时/熔断)相对薄弱**:需在薄编排层补足。

> 说明:方案B的劣势均为"工作流工程化"层面的可补齐项,不影响其作为底座的成立;且可通过"借一层薄确定性编排 + 按需 DeerFlow"系统化弥补。方案A 的工作流优势恰恰是方案B 最值得吸收的部分。

## 六、关键约束与大模型选型建议

### (一)关键约束

1. **本地私有化部署(约束)**:全链路须满足本地运算、本地归档,符合水利信创与数据安全要求。需注意:此为**部署形态约束**(数据不出域),与"具体采用何种模型规格"相互独立。
2. **安全关键场景的自主性边界**:防汛调度、泄洪、错峰为责任重大决策,须遵循调度规程与签批制度。**人审签批须作为调度决策的强制前置环节,不得由系统自动跳过**;系统仅产出建议方案、多方案对比、风险提示与证据链,终审权在人。
3. **数字孪生仿真耦合**:洪水演进、水动力、多物理场仿真是独立的大型系统,初期不应直接对接真实物理仿真,**建议以可离线验证的调洪演算作为"孪生"替身,后续以可插拔接口对接真实模型**。
4. **评测先行**:多Agent集群须自建设之初即内建评测,各子Agent与编排层均需具备基准用例与达标门槛,未达标不得进入生产。

### (二)大模型选型建议(可配置项,非决定项)

大模型规格为可按需调整的建议项,不构成方案选型的决定性因素。建议如下:

1. **方案B 对模型规格最宽容**:大模型仅承担路由与自然语言表述,对推理与工具调用能力要求低,**本地 Qwen3-14B/32B 或 DeepSeek-V3(蒸馏版)即可胜任**;条件允许时换用更强模型可进一步提升表述质量,但非必需。
2. **方案A 对模型规格要求较高**:其范式依赖高可靠的结构化工具调用与多跳推理,**建议采用 32B 及以上本地模型,或 DeepSeek-V3 等强模型**;若推理可靠性不足,需引入云端增强。
3. **混合部署(可选)**:在本地私有化前提下,对调度决策等推理密集环节,可采用"本地为主 + 受控云端增强"的混合形态(须另行评估合规与数据出境)。
4. **综合建议**:无论采用哪种方案,水利安全关键系统建议在本地私有化前提下,**选用可本地部署的最强模型(如 Qwen3-32B / DeepSeek-V3)**;其中方案B 因架构特性,对模型规格更宽容、运行成本更低,这也是其架构优势的体现。

## 七、选型建议

### (一)推荐方案

**建议采用方案B:以 Hermes + Skill 体系为底座,在工作流环节引入一层轻量确定性编排,并按需调用 DeerFlow 动态工作流。**

具体构成:

- **领域智能 → Skill**(规则 + 算法 + Python 实现 + 评测 + 进化参数),此为不可动摇之原则,系可靠性与可审计性的根本;
- **闭环控制流 → 主管 Skill 内置的薄确定性 DAG**(显式时序 + 分支规则 + 状态文件 + 断点续跑),**不交由大模型动态路由**;
- **多方案并行推演、自进化扫参 → 按需调用 DeerFlow 动态工作流 / autoresearch**;
- **结果仲裁 → 确定性优先级规则**(安全 > 水情 > 设备;超限即触发应急),不依赖大模型仲裁。

### (二)6类子Agent的落地映射(复用为主,新建为辅)

| 集群角色 | 复用既有 | 是否新建 |
|----------|----------|----------|
| 水情感知 | `powerelf-monitor` + `powerelf-early-warning` | 复用 |
| 大坝安全 | `powerelf-inspection` + `powerelf-monitor`(渗流/渗压/GNSS) | 复用 |
| 设备运维 | `powerelf-inspection` + 闸门泵站状态规则 | 复用 |
| 孪生推演 | — | **新建:调洪演算 Skill**(可插拔接口,后续接水动力) |
| 调度决策 | `powerelf-chatbi`(取数)+ 水库分析规则 | **新建:方案生成 Skill,含强制人审门** |
| 报告归档 | `powerelf-inspection` 报告生成模块 | **新建:汇总+台账+推送薄包装 Skill** |
| 主管调度 | — | **新建:主管调度 Skill(内置薄 DAG + 确定性仲裁 + 断点续跑)** |

即:实际新建 **3个领域 Skill + 1个主管 Skill**,其余3类角色直接复用。

### (三)采纳方案A 的适用条件

需客观说明:在剥离模型因素后,方案A 较此前更具竞争力。当以下条件**同时**成立时,方案A 可作为备选:

1. **系统复杂度主要在工作流机制本身,而非领域规则**(本系统不满足——复杂度集中于水利领域);
2. **无既有可复用资产,或明确接受重建成本**(本系统不满足——已有丰富 Skill 资产);
3. **团队具备 LangGraph 工程能力,且接受新增独立服务的运维负担**。

经核实,我方**前两项条件均不成立**,故方案A 不作为推荐方案。但其"显式编排闭环""成熟断点续跑与人机协同"等设计思想,应在方案B 的薄编排层中充分吸收。

## 八、实施路径建议

建议分三期推进,每期均可独立验收、风险可控:

| 阶段 | 目标 | 范围 | 关键交付 |
|------|------|------|----------|

| **二期(增强)** | 接入真实仿真与全角色 | 可插拔孪生接口对接水动力模型;补齐设备运维角色;实现断点续跑 | 暴雨连续过程可中断、可续跑 |
| **三期(完善)** | 日常精细化与多目标 | 日常巡检日报台账;蓄水/供水多目标平衡;报告/台账/推送全闭环 | 全场景覆盖,常态化运行 |

## 九、结论

1. 经多维度对比,在本系统复杂度集中于水利领域规则、且既有 Skill 资产丰富的现实下,**方案B(Hermes + Skill + 薄编排层)在资产复用、领域承载、自进化、评测、安全、运维、周期等关键维度上全面占优**,且其短板均可通过薄编排层与 DeerFlow 系统化弥补。
2. 方案A 在工作流引擎、断点续跑、人机协同、多分支回放等方面确为成熟强项;但其无法原生复用既有领域资产、需重建平台级能力,整体逊于方案B。其工作流设计思想应在方案B 中吸收。
3. 大模型规格为可配置建议项而非决定项;建议在本地私有化前提下选用可本地部署的最强模型(如 Qwen3-32B / DeepSeek-V3),方案B 对模型规格更宽容、成本更低。
4. **建议以方案B 立项推进**,按"一期试点—二期增强—三期完善"分步实施,坚持"领域智能 Skill 化、主链路确定性编排、人审强制前置、评测先行"四项原则。
